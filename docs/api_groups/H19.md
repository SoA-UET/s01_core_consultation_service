# H19 Group

## Overview

This is the group of HTTP APIs between the **Customer Web / End User Client**
and [**S01 - Consultation Service**](../services/core/S01_Consultation_Service.md).

This API group supports:

- **UC-03:** "Nhận tư vấn - tra cứu - hỏi đáp", which consists of:
  - **UC-03.1:** "Nhận tư vấn qua tin nhắn văn bản (text)"
  - **UC-03.2:** "Nhận tư vấn qua kênh thoại thời gian thực (audio)"
- **UC-04:** "Xem lịch sử tư vấn (xem các cuộc hội thoại)"
- **UC-05:** "Đánh giá chất lượng dịch vụ"

The APIs are designed following RESTful principles and focus on
the listed use cases.

## Design Principles

- REST (HTTP) for:
  - resource management
  - message submission
  - history retrieval
  - ratings

- Socket.IO for:
  - real-time audio streaming
  - real-time text streaming

## HTTP Endpoints

Endpoints denoted with "AUTH"
means that it must be authenticated
using JWT.

[How to verify JWTs](../auth/VERIFY.md)

### POST AUTH /api/v1/conversations

Create a new consultation conversation.
The same conversation could be used
for text and audio (one mode at a time).

Request body format:

```ts
{
    "title": string, // title do người dùng đặt, e.g. "Tư vấn gói cước"
}
```

Response body format:

```ts
{
    "content": {
        "id": string, // ID of the conversation
        "title": string, // e.g. "Tư vấn gói cước"
        "customer_id": string, // ID of the currently authenticated customer
        "status": string, // one of `AI_AGENT_TEXTING`, `AI_AGENT_CALLING`, `FORWARDING`, `HUMAN_AGENT_TEXTING`, `HUMAN_AGENT_CALLING`.
        // Initially, status would be `AI_AGENT_TEXTING`.
        "partner_id": string, // ID of the forwarded partner. Initially this is empty.
        "customer_satisfaction": number, // ranging from 1 to 5. Initially 5.
        "summary": string, // the conversation summary up to this point. Initially this is empty - since there is no message yet!
        "created_at": datetime, // e.g. "2025-12-08T10:30:00Z"
        "updated_at": datetime
    }
}
```

```ts
    }

```

### POST AUTH /api/v1/conversations/{conversation_id}/messages

Send a text message from customer to consultant.

Request body format:

```ts
{
    "content": string, // e.g. "Gói cước SD-70 có giá bao nhiêu?"
}
```

Response body format:

```ts
{
    "content": {
        "id": string, // ID of the message,
        "conversation_id": string, // ID of the conversation which this message belongs to
        "sender_type": string, // The sender type, one of: `CUSTOMER`, `AI_AGENT`, `HUMAN_AGENT`. Here it would be `CUSTOMER`.
        "sender_id": string, // The sender ID - this only exists when sender_type is HUMAN_AGENT
        "sender_name": string, // The sender name - this only exists when sender_type is HUMAN_AGENT
        "content": string, // e.g. "Gói cước SD-70 có giá bao nhiêu?"
        "created_at": datetime, // Message creation time, e.g. "2025-12-08T10:30:00Z"
    }
}
```

### POST AUTH /api/v1/conversations/{conversation_id}/audio

This is to submit whole audio input
from the customer, in AI Agent mode
only (i.e. not used when the conversation
is in `HUMAN_AGENT_TEXTING` or `HUMAN_AGENT_CALLING`
statuses). More information will be provided
in later sections.

Request:

- Header `Content-Type: multipart/form-data`
- Form fields: `file: recording.wav`
- Audio requirements:
  - Encoding: `PCM16`
  - Sample rate: 16 kHz
  - Channels: Mono
  - Container: WAV (PCM16, little-endian)

Server behavior:

- Validate conversation status currently == `AI_AGENT_CALLING`
- Reject otherwise (400)
- Accept full file
- Submit to another service for further processing (specified in S01)
- Return 202 Accepted.

The response body is empty.
AI processing results are delivered asynchronously via Socket.IO text events
(below).

## Socket.IO

Socket.IO is used for real-time, bidirectional communication
between the Customer Web / End User Client
and S01 - Consultation Service.

It supports:

- Real-time audio streaming
- Real-time text streaming

Socket.IO is NOT used for:

- CRUD operations
- Message persistence
- History retrieval
- Ratings

Those are handled via REST.

### Connection

The client establishes a Socket.IO connection to `/socket.io`

Authentication is done using JWT.

If authentication fails, the server MUST reject the Socket.IO connection.

### Authentication

JWT must be provided via Socket.IO `auth` payload.

Example:

```js
io("/", {
  auth: { token: "<JWT>" }
});
```

### Namespace

Namespaces are intentionally avoided for simplicity.

All events are sent over the default namespace - probably `/`.

### Room Model

Each conversation maps to one Socket.IO room:

```py
room = f"{conversation_id}"
```

That is, room name equals the conversation ID string and is globally unique.

- Client joins exactly one room at a time.
- To join another room, client makes sure to leave the one joined previously, if any.
- Server emits events to corresponding rooms as messages arrive (from customer or the other end - AI or a human consultant).
- Audio and text always belong to a particular conversation.

### Real-time Text and General Events Streaming

This is used for:

- live human agent replies
- AI partial responses
- system messages

REST `POST AUTH /api/v1/conversations/{conversation_id}/messages` (specified above) is still used for final / persisted messages.

For streaming events below, chunks are emitted in order.
`text_stop` terminates the current message stream.

For human agent, since the whole message
has already been sent via REST endpoint above,
the Socket.IO events need not to divide
the message into chunks. Instead, only
three events are emitted in sequence:

- `text_start`
- `text_chunk` (with whole message content)
- `text_stop`

#### Socket.IO Text Event: `text_start`

Indicates the beginning of a new message.

Server → Client only:

- event: `text_start`
- payload:
  
    ```ts
    {
        "conversation_id": string
    }
    ```

#### Socket.IO Text Event: `text_chunk`

Carries the message whole content,
or partial content ("chunk") in case
of AI Agent's output.

Server → Client only:

- event: `text_chunk`
- payload:

    ```ts
    {
        "conversation_id": string,
        "timestamp": number,    // Unix timestamp in ms (capture time)
        "sender_type": string, // The sender type, one of: `AI_AGENT`, `HUMAN_AGENT` (since `CUSTOMER` message is not sent through this API!)
        "sender_id": string, // The sender ID - this only exists when sender_type is HUMAN_AGENT
        "sender_name": string, // The sender name - this only exists when sender_type is HUMAN_AGENT
        "content": string    // e.g. "chào, chúng tôi " - partial text
    }
    ```

#### Socket.IO Text Event: `text_stop`

Indicates the end of the message's (partial)
content stream.

Server → Client only:

- event: `text_stop`
- payload:

    ```ts
    {
        "conversation_id": string
    }
    ```

#### Socket.IO General Event: `status_switch`

Indicates that the conversation is now switching
status.

Server → Client only:

- event: `status_switch`
- payload:

    ```ts
    {
        "conversation_id": string,
        "old_status": string, // one of `AI_AGENT_TEXTING`, `AI_AGENT_CALLING`, `FORWARDING`, `HUMAN_AGENT_TEXTING`, `HUMAN_AGENT_CALLING`
        "new_status": string
    }
    ```

Conversation status is authoritative and server-controlled.
Clients MUST NOT change conversation status directly.
Clients MUST react to `status_switch` events emitted by the server.

### Real-time Audio Streaming

Real-time audio is streamed using **Socket.IO binary messages**.
Each audio message carries a **single fixed-duration PCM frame**.

Audio is unidirectional per event, but the same event structure is used in both directions.

Audio format:

- Encoding: PCM (signed integer)
- Endianness: Little
- Sample rate: 16000 Hz
- Channels: 1 (mono)
- Sample width: 16-bit (int16)
- Container: Raw PCM (no WAV header)

This format is chosen because it is trivial to generate, decode, and play on both browser and backend.

Frame size:
- Each audio frame represents 20 ms of audio.
- Calculation:
    - 16,000 samples/sec × 0.02 sec = 320 samples
    - 320 samples × 2 bytes = 640 bytes per frame
- So, each audio chunk MUST be exactly 640 bytes

Transport Encoding:
- Audio is sent as binary data.
- **NO base64 encoding**
- Socket.IO automatically handles binary frames
- Payload type:
  - Browser: `ArrayBuffer`
  - Python (Flask-SocketIO): `bytes`

Socket.IO events:

#### Socket.IO Audio Event: `call_start`

Indicates the beginning of a call session.
Client → Server only:

- event: `call_start`
- payload:

    ```ts
    {
        "conversation_id": string
    }
    ```

#### Socket.IO Audio Event: `call_end`

Indicates the end of a call session.
Client → Server only:

- event: `call_end`
- payload:

    ```ts
    {
        "conversation_id": string
    }
    ```

#### Socket.IO Audio Event: `audio_start`

Indicates the beginning of an audio stream.

Client → Server, or Server → Client:

- event: `audio_start`
- payload:

    ```ts
    {
        "conversation_id": string
    }
    ```

#### Socket.IO Audio Event: `audio_chunk`

Carries exactly one PCM frame (20 ms).

Client → Server, or Server → Client:

- event: `audio_chunk`
- payload:

    ```ts
    {
        "conversation_id": string,
        "timestamp": number,    // Unix timestamp in ms (capture time)
        "audio": ArrayBuffer    // EXACTLY 640 bytes of PCM data
    }
    ```

Partial PCM frames MUST NOT be sent. The final frame MUST
be padded with silence to 640 bytes, or omitted
entirely before `audio_stop`.

#### Socket.IO Audio Event: `audio_stop`

Indicates the end of the audio stream.

Client → Server, or Server → Client:

- event: `audio_stop`
- payload:

    ```ts
    {
        "conversation_id": string
    }
    ```

#### Socket.IO Audio Event: `audio_file`

This event is used to transmit a whole audio file
(from server to client) - e.g. Text-to-Speech output.
It is NOT used for real-time streaming (for that,
use the three events `audio_start`, `audio_chunk`, and `audio_stop` above).

Server → Client only:

- event: `audio_file`
- payload:
  
    ```ts
    {
        "conversation_id": string,
        "mime_type": string, // e.g. "audio/mpeg"
        "audio": ArrayBuffer    // the whole audio file in WAV format
    }
    ```

### CRITICAL NOTICE

Audio handling is strictly determined by conversation status:

- in `AI_AGENT_CALLING` the client records full utterances and
    uploads audio files via HTTP;

- in `HUMAN_AGENT_CALLING` the client streams fixed-size PCM
    frames via Socket.IO.

These modes are mutually exclusive and must never be mixed.
The server MUST reject audio input that does not match
the current conversation status.

To get notified of the current conversation status,
rely on the event `status_switch` above.

To stream PCM frames, use the aforementioned
Socket.IO API, with `audio_start`, `audio_chunk`,
and `audio_stop` events.

To record full utterances in the browser,
use the VAD library: `yarn add @ricky0123/vad-web`
and possibly also `yarn add @ricky0123/vad-react`.
And instead of using those three events for
audio chunking, use the `POST AUTH /api/v1/conversations/{conversation_id}/audio`
endpoint above.

The following are NOT allowed:
- Mixing HTTP audio upload and Socket.IO audio streaming
- Sending audio frames outside `HUMAN_AGENT_CALLING`
- Sending partial PCM frames
- Persisting streamed audio frames as messages in database.
    Instead, forward the audio chunks immediately and
    discard them.

### Bonus: Client (Browser) Receiving Audio Chunks

1. Receiving audio

    - Upon receiving `audio_chunk`:
      - Extract audio (ArrayBuffer)
      - Interpret it as Int16 PCM
      - Convert to Float32
      - Push into a playback buffer
      - Play via Web Audio API

    - Reference decoding logic (conceptual):

        ```js
        const pcm16 = new Int16Array(audioBuffer);
        const float32 = new Float32Array(pcm16.length);

        for (let i = 0; i < pcm16.length; i++) {
        float32[i] = pcm16[i] / 32768;
        }
        ```

2. Playback

    - Use AudioContext
    - Create an AudioBuffer
    - Write decoded samples
    - Schedule playback slightly in the future (jitter buffer)
    - Clients SHOULD buffer 2–4 frames (40–80 ms) before playback
        to reduce jitter.
    - Conceptual code:

        ```js
        const audioBuffer = audioContext.createBuffer(
        1,
        float32.length,
        16000
        );

        audioBuffer.copyToChannel(float32, 0);
        ```
